Analyse & Conclusions

REST — Points forts observés

  • Throughput supérieur en local (×1.9 en lecture, ×1.9 en ramp)
  • Latence médiane plus basse sur les lectures simples
  • Pas de surcoût de connexion HTTP/2 pour les faibles charges
  • Gin (HTTP/1.1) très optimisé pour le mode keep-alive local
  • Outillage universel (curl, Postman, browser)

gRPC — Points forts observés & contextuels

  • Payload 41 % plus compact (135 B vs 230 B) → bande passante réduite
  • Latence écriture inférieure (p99 −46 % sur scénario B)
  • Scalabilité linéaire ghz : +64 % throughput 10→100 connexions
  • Avantage HTTP/2 prononcé sur WAN (latence réseau élevée)
  • Contrats forts (proto), streaming bidirectionnel, load-balancing L7
Interprétation : En environnement local loopback, REST (Gin/HTTP 1.1) surpasse gRPC sur le throughput brut car le multiplexage HTTP/2 n'apporte pas de gain lorsque la latence réseau est quasi-nulle et que les connexions sont déjà persistantes. L'avantage gRPC devient significatif dès qu'il y a de la latence réseau (services distribués, clouds multi-régions) : la compression Protobuf réduit les octets transférés et le multiplexage HTTP/2 évite le head-of-line blocking. Pour un usage microservices en production, gRPC est recommandé pour les communications inter-services à forte fréquence ; REST reste le choix naturel pour les APIs publiques exposées aux navigateurs.
